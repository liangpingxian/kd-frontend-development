# KD Frontend Development

This skill is the main entry point for the KWC project. It covers scaffold commands, metadata contracts, frontend/backend integration, and deployment.
**First time working with a KWC project**: read [`references/concepts.md`](./references/concepts.md) first (delivery targets / metadata-driven model / component–page relationship constraints); afterwards execute directly without re-reading.

## 🔴 Hard Rules (must not be violated)

1. **render cards must be generated by scripts**—any render:kdform card must be produced via `scripts/form-link.mjs`; manually assembling JSON is forbidden

## KWC Project Directory Structure

A project generated by `kd project init` uniformly follows the structure below (use this layout whether finding files or creating them):

```
<project-root>/
├── .kd/                                    CLI config (contains config.json, including the framework field)
├── app/
│   ├── kwc/                                🔴 Frontend component directory
│   │   ├── <ComponentName>/                One directory per component
│   │   │   ├── <ComponentName>.tsx         Component code (vue/lwc projects use .vue / .js)
│   │   │   └── <ComponentName>.js-meta.kwc Component metadata
│   │   ├── ExampleComponent/               Built-in scaffold sample (**reference only, do not deploy**; remove its .js-meta.kwc when necessary)
│   │   ├── static/                         Static assets
│   │   ├── types/                          Type declarations (contains declarations.d.ts)
│   │   ├── index.html / main.tsx           Local preview entry (**not the delivery path**, see concepts.md)
│   │   └── tsconfig.json
│   ├── pages/                              🔴 Page metadata directory
│   │   └── <page_name>.page-meta.kwp       One file per page
│   └── ks/controller/                      🔴 Backend Controller directory (create on demand)
│       ├── <ControllerName>.kws            Controller metadata (route / method / permission)
│       └── <ControllerName>.ts             Controller script (KingScript)
├── dist/                                   Build artifacts (do not modify by hand)
├── scripts/                                In-project npm scripts
├── server.ts / vite.config.ts              Local preview related
├── package.json
└── README.md / README_zh.md
```

**Key path quick reference**:
- Find/write a **component**: `app/kwc/<ComponentName>/`
- Find/write **page metadata**: `app/pages/<page_name>.page-meta.kwp`
- Find/write a **Controller**: `app/ks/controller/<ControllerName>.{kws,ts}`
- Find **framework config**: `.kd/config.json` (the `framework` field tells react/vue/lwc)
- Find **type declarations**: `app/kwc/types/declarations.d.ts` (any new third-party package must `declare module` here)

**Do NOT do**:
- Do not manually create the directories/files above; always use `kd project create`
- Do not mount components directly onto `main.tsx` and treat that as "delivery complete"—delivery happens via `<controls>` in `app/pages/*.page-meta.kwp`
- Do not modify artifacts under `dist/`

## Phase Detection

Determine which step the current task belongs to in this order:

1. No `.kd/` in the current directory → treat as an uninitialized KWC project, go to "Initialize project"
2. User wants to create a component / page / Controller → use `kd project create`; do not manually assemble the directory
3. User wants to deploy / debug → run `kd project deploy` directly (default environment); only configure an environment if deployment fails complaining no environment exists
4. User starts writing frontend component code (*.tsx / *.vue / *.js) → **must read before coding** [`references/kwc-frontend-contract.md`](./references/kwc-frontend-contract.md); UI implementation details are up to you
5. User wants to write a backend Controller → go to [`kwc-ks-controller-development`](./kwc-ks-controller-development/SKILL.md)

## Automation Script Locations

Scripts live in the `scripts/` directory next to this SKILL.md. The AI knows the absolute path to SKILL.md when this Skill is loaded, so **call them by joining that path directly**—do not use `find` or similar commands to rediscover them (slow and prone to selecting the wrong clone).

In the text below, `$SKILL_DIR` refers to **the directory containing SKILL.md** (i.e. the Skill root). At execution time substitute it with the known absolute path, for example:

```bash
node <directory containing SKILL.md>/scripts/project-init.mjs ...
```

| Script | Purpose |

## Invoking the kd Command

Run `kd <subcommand>` directly in the shell.

## Code Implementation Responsibilities

### Frontend component code (*.tsx / *.vue / *.js)

**Free to implement**—how to write React/Vue/LWC, which UI library to use (Shoelace / native div / ECharts, your choice), how to lay things out: decide based on the business need.

**The only hard constraint**: comply with the KWC framework contract. **Must read before coding** [`references/kwc-frontend-contract.md`](./references/kwc-frontend-contract.md) (≤80 lines, covers KwcConfig props shape, the `config` field, adapterApi call entry point, declarations.d.ts, main.tsx not being the delivery path).

### Backend Controller script code (*.ts)

**Do not write it on your own based on general Node/Java experience**—the KingScript runtime is completely different from Node.js / Java Servlet, and the SDK is a closed ecosystem. **Must read before coding** [`kwc-ks-controller-development/SKILL.md`](./kwc-ks-controller-development/SKILL.md) along with its rule.md / reference/. For SDK lookup, see [`kingscript-code-generator/SKILL.md`](./kingscript-code-generator/SKILL.md).

## Initialize Project

Must be done with `project-init.mjs` in one shot. Do not execute `kd project init` directly (it is interactive).

```bash
cd <target parent directory absolute path> && node $SKILL_DIR/scripts/project-init.mjs --name <project name> --framework react --language ts --app <application code>
```

- Required: `--name` / `--framework` / `--language` / `--app`
- **The project is generated under `cwd/<name>` at call time**, so you must `cd` to the target parent directory beforehand (the script no longer provides `--cwd`, to avoid path-validation ambiguity)
- The script does **not** run `npm install` by default; after initialization completes, instruct the user to manually run `cd <project directory> && npm install --registry=https://registry.npmmirror.com` (China mirror for speed)
- Defaults to `react` + `ts`; when the user explicitly specifies Vue/LWC, follow that

## Create Component / Controller / Page

```bash
kd project create <ComponentName>  --type kwc          # Component
kd project create <ControllerName> --type controller   # Controller (-e <env> optional, specifies the environment to pull the SDK from)
kd project create <page_name>      --type page         # Page
```

**Must do after creation**:
1. Immediately fill in the `.js-meta.kwc` / `.kws` / `.page-meta.kwp` template fields (this is the responsibility of this Skill: metadata first)
2. Read the matching contract document before writing code (frontend → kwc-frontend-contract.md; Controller → sub-skill)

For detailed metadata field rules: [`references/component-metadata.md`](./references/component-metadata.md) / [`references/page-metadata.md`](./references/page-metadata.md) (must read on first contact with the project; reusable thereafter).

Key constraints on page metadata:
- `<control type>` must **exactly match** the component metadata `name` (case-sensitive); do not add a `kwc_` prefix just because the directory is under `app/kwc/`
- Page `name` ≤ 20 characters (the system will prepend the ISV prefix)
- Newly generated `page-meta.kwp` contains only a comment template by default; you must actively fill in `<controls>`

## Inputs the User Must Supply

When something cannot be inferred, stop and ask, providing 2–4 explicit options:

- Project name / existing project path
- Cosmic application code `app` (**the single authoritative definition for this entire document**):
  - Must be explicitly provided by the user or come from `.kd/config.json`; **never guess, never use example values**
  - Standard format `{isv}_{appName}` (e.g. `kdtest_kwc_test`); apps starting with `kingdee` are an exception
  - If the ISV prefix is missing and it does not start with `kingdee`, you must confirm with the user
- Target environment alias and URL (only when no environment is configured)
- Authentication parameters (only when the environment is not yet authenticated)
- Page identifier and business purpose
- Which component parameters should be exposed as configurable properties

`isv` exception: it may be left empty during development; `kd project deploy` writes it automatically from the environment.
Framework exception: when unspecified, default to `react` + `ts`—no need to ask.
Deployment is not a sensitive action; **after creating a component/page, deploy automatically by default**. Sensitive actions like delete/release must be confirmed first.

## Decisions the Skill Makes Automatically (do not bounce back to the user)

- Business requirement → component breakdown (typically 1 requirement = 1 component + 1 page)
- Component PascalCase name / lowercase page identifier / unique instance name
- Inference of `<property>` items that should be exposed in component metadata
- Current phase detection (init / create / deploy / open / debug)
- Incrementing the `version` of the corresponding file when metadata changes

## Controller End-to-End Self-Check (🔴 hard gate)

After a Controller deploys successfully, you **must** run [`scripts/test-controller.mjs`](./scripts/test-controller.mjs) to self-check; **before it passes, do not write frontend adapterApi integration code**. Full flow in [`references/controller-e2e-check.md`](./references/controller-e2e-check.md) (account configuration, command modes, validation standards, the 3-retry cap and how to handle exceeding it).

3 failures → fall back to implementing with frontend mock data.

## End-to-End Execution Pipeline

When the user says "help me develop a KWC page/feature", proceed by default along this line:

0. **Immediately send the development-state signal** (see "Development-state animation signal" below)
1. Detect new project / existing project; collect environment inputs that cannot be inferred
2. Assess whether backend data interaction is involved; if so, plan the Controller
3. Create the component project (and, when needed, the Controller too)
4. Fill in all metadata: `.js-meta.kwc`, `.kws` (if any)
5. Implement the frontend component code (must read [`references/kwc-frontend-contract.md`](./references/kwc-frontend-contract.md))
6. If there is a Controller: implement the script (must read [`kwc-ks-controller-development`](./kwc-ks-controller-development/SKILL.md)) → `npm run build:controller` (local compile only) → `kd project deploy` (actual upload) → run test-controller.mjs self-check (must pass)
7. Create and fill in page metadata
8. `kd project deploy` (default environment, no need to ask)
9. **Send the render card** (see below)
10. [Optional] `kd open` / `kd debug` only when the user explicitly requests them

### Development-state animation signal (render:kdapp)

When the end-to-end development pipeline starts, the **first response** must first invoke the `output_check` tool, then paste the animation signal as **the model's text output** into the reply body. Two steps:

**Step 1 — run the script to obtain that line of string**:
```bash
node $SKILL_DIR/scripts/app-signal.mjs --title "<auto-summarized from the user's requirement>"
```

**Step 2 — paste the stdout line of the script verbatim into your text reply** (standalone paragraph with blank lines before and after; not inside a code block / quote block / backticks; no characters appended on the line).

> ⚠️ **Key concept**: The Bash tool's stdout is only a tool result, **and the frontend does not render tool results**, it only renders the model's text output. So after running the script, you **must** repeat that line in the text reply—otherwise it counts as not sent. When repeating, **copy character-for-character**: do not change formatting, do not interpret, do not summarize it into "animation already on".

**Other rules**:

- **Do not manually assemble** `:::render:kdapp ...:::`; it must go through the script (the script handles formatting and title length validation)
- **`title` is auto-generated by the model**—do not ask the user, do not hard-code it. An 8–14-character business summary, e.g. "Sign-in Duration Query Page", "Customer Profile Entry", "Inventory Count Entry"
  - Source priority: ① the user's latest explicit request → ② recognized entity/field → ③ component/page name already created → ④ fallback "KWC Page Development"
- **When a sub-agent runs the script**: stdout exists only inside the sub-agent context; the sub-agent must **return that line character-for-character to the main agent**, and the main agent writes it into the user-facing text reply; if it cannot be returned, the main agent re-runs the script and pastes it
- **Emit only once per end-to-end pipeline**: do not repeat between now and the final render:kdform card output; the animation is automatically closed by the frontend based on the kdform card, **do not send a close signal**
- **Trigger boundary**: the user says "develop again / new / help me build a …", or in a new conversation modifies a deployed page → treated as a new pipeline, emit again
- **Does not trigger**: pure troubleshooting / querying / explaining, simply running a script, the user only wants to see progress
- This signal and the final render:kdform are two independent instructions; they do not replace each other

### When to emit the render card

```bash
node $SKILL_DIR/scripts/form-link.mjs generate --pageMeta <page metadata file path> [--formNumber <entity code>] [--env <environment name>]
```
- Before output you **must first call the `output_check` tool**
- **Do not manually assemble** `:::render:kdform ...:::` JSON; you must generate it with the script
- **The script stdout must be pasted verbatim into the final user-facing reply body**: the complete `:::render:kdform ...:::` line, standalone, not inside a code block / quote block / backticks. Repeating it as "the access link has been generated" or pasting a plain hyperlink will not render the card and counts as not sent
- **When a sub-agent runs the script**, stdout is only in the sub-agent context; it must return that line character-for-character to the main agent, which pastes it verbatim into the reply; if it cannot be returned, the main agent re-runs it
- **Frontend-only task** (no Controller): emit immediately after a successful deploy
- **Task with backend** (with Controller): only emit after the Controller self-check passes + the frontend adapterApi integration code has been deployed. If the Controller has failed 3 times and decision is handed back to the user, **emission is likewise forbidden**
- **New conversation modifying a deployed page**: after the modification is deployed, **you must re-emit** (even if it was emitted before)

## Output Requirements

Each time you output a plan or command, also provide:
- Current phase + the next command
- Key inputs still needed from the user
- Whether it depends on existing environment authentication / whether `page-meta.kwp` needs editing / whether the metadata version needs incrementing
- Whether the **first response** of the end-to-end pipeline has invoked `output_check` and emitted `:::render:kdapp ... "phase":"developing"}:::` (once per pipeline; must end with `}:::`)
- Whether the conditions for sending the render card are met, whether `output_check` was invoked, and whether it has been sent

### Progressive flush (preventing long silent timeouts)

For large requirements, do not "write all files at once before speaking"—you must output in segments at this cadence:

- **Within a single response, write at most 2 files in a row**, or up to a cumulative ≤ 200 lines of code; once the limit is hit, output a progress line first (e.g. "X.tsx is done, writing X.js-meta.kwc next") before continuing.
- **Mandatory break-points at these boundaries** (end the previous segment → output text → enter the next segment):
  1. Between metadata (`.js-meta.kwc` / `.kws` / `.page-meta.kwp`) ↔ business code (`.tsx` / `.vue` / `.ts`)
  2. Between frontend component ↔ Controller script
  3. Between any code block ↔ `kd project deploy`
  4. Between `kd project deploy` ↔ the `test-controller.mjs` self-check
  5. Self-check passes → call `output_check` → emit the render card
- **Long-running commands** (`npm install` / `kd project deploy` / `test-controller.mjs`) get a response to themselves, with one line of explanation before and after; do not cram them into the same round as file writes.
- The progress line at a break-point should be brief (one sentence is enough), stating: what was just done, what is next, and whether the user's confirmation is needed.
